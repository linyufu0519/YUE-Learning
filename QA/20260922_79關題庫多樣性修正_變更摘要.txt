================================================================================
  康軒六上 79 關題庫 — 主題錯配與重複性修正變更摘要
  日期：2026-09-22
================================================================================

【USER 需求】
  家長實際使用時發現不同關卡反覆出現相同題型，只替換數字，部分題目也沒有真正
  對應關卡名稱。需將題庫改為以每一關的主題設計，增加數值、人物、物品與生活情境
  變化，讓基礎、進階、挑戰不只是數字變大，而是有直接辨識、反推與多步驟應用差異。

  5-Whys 根因：
  1. 孩子反覆看到相同題型，因為同單元不同關卡共用同三個模板。
  2. 關卡只傳入 generatorKey，topic 沒有決定實際運算。
  3. 數字由線性公式遞增，題目外觀容易預測。
  4. 測試只確認 ID、答案與 topic 文字存在，沒有驗證數學運算是否符合主題。
  5. 題庫缺少「每個 topic 的 operation contract」與答案不變量，套皮題仍會通過。
  根因類型：題庫資料模型與品質門檻的設計缺口。

--------------------------------------------------------------------------------

【影響範圍】

  程式位置一：js/stage-question-engine.js
  函式／區塊：關卡題目 strategy registry、seeded 題目參數、難度模板
  說明：產生 79 關各難度的選擇題與輸入題。
  異動：由單元共用三模板改為依關卡主題選取專屬數學策略；使用關卡、難度及題目序號
        產生穩定但不呈線性遞增的亂數參數，並輪替人物、物品與生活情境。

  修改前：
    GENERATORS[stage.generatorKey][index % 3]
    n = 40 + index * 6 + difficultyOffset + variant * 1000

  修改後：
    依 stage.topic 取得主題策略與三種以上模板
    由 stageId + difficulty + index 建立 deterministic seeded PRNG
    easy 使用直接辨識／計算，medium 使用反推／換算，hard 使用多步驟／生活應用

  ─────────────────────────────────────────────────────────────────────────────

  程式位置二：tests/stage-question-engine.test.js
  函式／區塊：全 79 關題庫品質回歸
  說明：防止未來再次只靠換數字或在題目前加主題名稱通過測試。
  異動：逐關驗證主題策略、三種題型概念、難度複雜度、50 組唯一題目、同次十題去重、
        同單元跨關卡差異及代表性答案正確性。

【測試建議】
  1. 第1單元「質數與合數」只出質合數辨識／判斷，不出最大公因數題。
  2. 同單元任取兩關，比較十題 prompt 與解法，確認不是同模板只換主題標籤。
  3. 同一關連續抽兩組十題，確認沒有完全相同的 prompt＋answer。
  4. 比較 easy／medium／hard，確認題目由直接計算進展到反推或多步驟情境。
  5. 全 79 關各難度抽樣至少 50 題，確認答案、提示、解析與選項有效。

【追加修正：生活情境語意】
  家長抽樣發現 hard 題雖已改為主題專屬運算，但題目前綴仍統一使用「在某處準備
  彩帶時，遇到這題」，造成速率、比、圓與比例尺等題目語意不搭，也形成新的重複樣板。

  修正方式：
  1. 移除通用的「準備彩帶／遇到這題」包裝句。
  2. 將每個有效 topic 明確映射至貼合內容的情境 profile，例如速率使用交通／運動
     行程，比與比值使用調飲／分裝配方，圓周使用輪子／花圈，比例尺使用地圖／模型。
  3. 每個 profile 提供三種開場句，依題目 index 穩定輪替，保留人物與地點變化。
  4. 新增全 79 關 hard 題情境契約測試，同時檢查主題關鍵語意、三種句型輪替及舊
     通用開場不得再出現。

--------------------------------------------------------------------------------

【追加修正：同組十題的思考方式】
  使用者再次實際驗收發現，文字情境雖自然，但一組十題的解題方式仍高度相同。

  5-Whys 根因：
  1. 十題看似不同卻可用同一方式秒答，因為差異主要來自數值與敘述。
  2. 每個固定難度只有三個 operationKey，並以 index % 3 循環。
  3. 50 題池因此是三個結構重複套參數，不是 50 種思考方式。
  4. selectStageQuestions 僅隨機抽題，沒有結構配額或覆蓋保證。
  5. 測試只檢查 prompt+answer 唯一，未量測認知操作與解題步驟。
  根因類型：題池結構模型及選題演算法缺少認知多樣性約束。

  修正方式：
  1. 每個主題原有三個數學 operation 再搭配 solve、select、verify 三種認知操作，
     每關每難度形成至少九個結構模板。
  2. 新增結構指紋：operationKey + cognitiveMode + type + solutionSteps。
  3. 抽十題時先依結構指紋分組，再以輪抽配額選題，避免隨機集中同一模板。
  4. 新增全 79 關 × easy/medium/hard 的實際十題 UX 驗收，要求至少六種結構、
     三種認知操作、兩種作答型態，並同時包含原始解題、選擇與判斷。

--------------------------------------------------------------------------------

【追加修正：完整題幹語意品質】
  實際題目仍出現前綴人物與題幹人物不同、不可排列物品被描述為「每排」、第二步條件
  未明講等問題。此問題會增加孩子理解負擔，屬題意正確性缺陷。

  5-Whys 根因：
  1. 一題出現兩位主角，因 buildQuestion 在完整題幹外再加一層人物前綴。
  2. 前綴與題幹分別選人物，兩層生成器互相不知道對方內容。
  3. 所有領域共用同一物品詞庫，沒有區分可排列、可秤重及可分裝物品。
  4. hard 題用「增加兩排」省略每排數量不變的條件，依賴讀者自行推測。
  5. 原測試只找情境關鍵字，沒有檢查主角數、禁用套語、物品動作及條件完整性。
  根因類型：情境責任分散、詞彙未型別化及語意品質門檻缺漏。

  修正方式：
  1. 移除 buildQuestion 的第二層人物／地點前綴，完整題幹只由 operation generator 產生。
  2. 判斷題不再新增「同學」主角，改為直接要求先解原題再判斷指定答案。
  3. 通用計數物品限縮為積木、卡片、貼紙與餅乾；各單位題維持專屬材料。
  4. 質合數兩步驟題明寫「每排仍放相同個數」，並以積木作為可排列物品。
  5. hard 標籤改為「生活應用與挑戰」，避免不是每題都恰為兩步時造成錯誤標示。
  6. 全 79 關 hard 各抽 50 題，檢查單一主角、禁用套語、主題證據、非法數值及
     質合數題的完整條件。
